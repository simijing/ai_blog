## 内容应该放在哪里

做这个博客时，我先犯了一个错误：把文章直接写进 HTML。写完第二篇我就发现，每改一次排版，都要动所有文件。于是我把正文抽出来，存成独立的 Markdown 文件，页面只负责取数据和渲染。

这个决定让整个站的结构简单了很多：

```text
content/
└── posts/
    ├── hello-world.md
    └── markdown-driven-blog.md
js/
├── config.js     # 文章元数据
├── markdown.js   # 极简解析器
├── renderer.js   # 页面与列表渲染
├── router.js     # hash 路由
└── app.js        # 交互与渲染入口
```

`config.js` 里维护每篇文章的标题、日期、分类、标签和摘要，Markdown 文件里只写正文。这样做的直接好处是：改标题不用进正文，换渲染器也不影响内容。

## 元数据放在 JS 里

之所以不用 YAML front matter，是因为浏览器不认识它，还得额外写一段解析。既然只是一个个人博客，用 JavaScript 数组最直接：

```js
var SITE_CONFIG = {
  posts: [
    {
      slug: "hello-world",
      title: "你好，世界：这个博客的第一篇文章",
      date: "2026-10-20",
      category: "随笔",
      tags: ["博客", "开始"],
      excerpt: "为什么在一切都追求即时反馈的时代，还要认真地搭一个博客？",
      published: true
    }
  ]
};
```

列表页按 `date` 倒序排一次，详情页按 `slug` 找到对应条目。元数据查找只是数组遍历，没有数据库；正文则按 slug 用 `fetch` 读取对应的 Markdown 文件。

## 一个够用的解析流程

真正的渲染分三步：

1. 用 `fetch` 取回 Markdown 文本；
2. 用一个自己写的函数把常见语法转成 HTML；
3. 把结果插入页面，并给代码块加上复制按钮、给标题生成 id。

取文件的部分只有几行：

```js
async function loadPost(slug) {
  const res = await fetch(`content/posts/${slug}.md`);
  if (!res.ok) {
    throw new Error(`文章不存在：${slug}`);
  }
  return res.text();
}
```

实际实现还会对 slug 做 `encodeURIComponent`，并处理 `file://` 协议，避免直接打开本地文件时请求失败。

解析器我只实现了自己会用到的语法，包括标题、段落、列表、引用、代码块、行内代码和链接。每增加一条规则，我都会在文章里实际用一次，确保它能工作。表格是最后加的，因为写部署对比时确实需要：

| 语法 | 处理方式 | 备注 |
| --- | --- | --- |
| `## 标题` | 生成 `h2` | 行首匹配 |
| 代码块 | 保留原文并转义 | 语言标记写入 class |
| 表格 | 按行拆分单元格 | 支持左、中、右对齐 |

> 自己写解析器的价值不在于省下一个依赖，而在于你会被迫读完 [CommonMark 规范](https://commonmark.org/) 里那些平时跳过的细节。

是的，它不可能覆盖所有边界情况，比如列表里的代码块、表格单元格中的换行。但我知道它坏在哪里，出了问题能定位，这比“看起来支持”更可靠。

## 代价与收获

- 代价：每加一种语法都要写测试，复杂排版会露怯；
- 代价：没有插件，代码高亮得自己接；
- 收获：页面加载快，几乎没有运行时依赖；
- 收获：内容是可移植的纯文本，随时能搬到别处。

如果哪天文章多到需要全文搜索和分页，我会考虑换成成熟的生成器。但在那之前，**这套只有几百行的实现，够用了**。

这套方案还有一个前提：我愿意维护一个自己写的解析器。它不难，但需要耐心，尤其是遇到别人写的不规范 Markdown 时。好消息是这个博客只有我一个人写，坏习惯也只有一个来源。

*内容和呈现分开之后，换主题才不至于重写文章。*
