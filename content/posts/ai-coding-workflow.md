## 把 AI 放在工作流的什么位置

关于 AI 编程的讨论容易走两个极端：要么认为它马上取代程序员，要么认为它只会生成废话。用了大半年之后，我的结论很平常：**它最擅长的是那些“我知道要做什么，但不想亲手敲”的部分**。定位清楚了，工作流也就清楚了。

我现在的分工大概是：人负责判断，模型负责展开。

## 三个阶段

### 读代码

接手陌生模块时，我很少直接让模型“解释这个文件”，那样得到的多半是逐行翻译。更有效的问法是：这个模块的入口在哪、数据从哪里来、失败时会发生什么。让模型先给出调用链，我再拿真实代码核对。凡是它说得含糊的地方，往往就是我自己还没读懂的地方。

### 写代码

我写需求时尽量带上约束，例如：

- 只改这个函数，不要动公共接口；
- 不新增依赖；
- 保持现有代码风格，错误处理沿用项目里的写法；
- 如果信息不够，先提问，不要猜。

最后一条最重要。模型在缺信息时倾向于补全，而补全的默认值经常和项目约定冲突。

### 验证

生成之后，验证仍然是我的工作。我通常按这个顺序检查：

1. `git diff` 看改动范围是否符合预期；
2. 跑一遍内容自检，或手动执行受影响的路径；
3. 看错误分支有没有被覆盖；
4. 确认没有悄悄引入新的依赖或配置。

```bash
git diff --stat
git diff -- js/
node tools/check-markdown.mjs
```

命令不复杂，但作用很大：**改动范围和自检结果，是判断这次生成能不能留下的唯一依据**。

## 提示词的结构

我习惯把任务拆成四段：背景、目标、约束、验收标准。写成清单比写成一段话更稳，因为模型不会漏掉你明确列出的约束。

```json
{
  "context": "静态博客，无构建步骤，原生 JavaScript（经典 script 顺序加载）",
  "goal": "为文章列表增加全文搜索",
  "constraints": ["不引入依赖", "保持 URL 可直接访问"],
  "acceptance": ["正文里的关键词也能搜到", "无匹配时显示空状态提示"]
}
```

这份 JSON 不是给某个工具读的，只是我自己的草稿格式。但它逼我把“验收标准”写出来——很多次，写不出来就说明我还没想清楚要做什么。

> AI 不会替你做决定，它只是把决定执行得更快。所以决定错的时候，它也错得更快。

## 我不用它做什么

- 不把整段业务逻辑交给它写，尤其是涉及钱和权限的部分；
- 不在看不懂 `diff` 的情况下合并；
- 不让它替我读官方文档的结论，最多让它帮忙定位要读哪一节。

*先问清楚，再让模型动手，是我目前最看重的一条纪律。*

这些限制看起来保守，但工作效率反而更高：少一次返工，就多一小时真正在思考的时间。
